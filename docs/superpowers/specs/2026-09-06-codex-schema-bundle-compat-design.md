# Codex App Server Schema Bundle Compatibility Design

## Status

Approved in principle by the project director on 2026-09-06. This document
records the exact implementation boundary before code changes begin.

## Context

The installed Gemini companion fails closed with `app_server_incompatible`
before a request reaches 9Router. The configured Codex Desktop App Server
version 0.153.4 successfully generates its protocol schemas, but the companion
rejects the generated directory because it contains 304 JSON files while
`readGeneratedSchemas` accepts at most 64.

The same output includes the canonical aggregate file
`codex_app_server_protocol.schemas.json`. It is 683,139 bytes and contains the
two definitions required by the current compatibility gate:
`definitions.ClientRequest` and `definitions.ServerRequest`.

This is an adapter qualification defect, not evidence that the Desktop App
Server protocol or the Gemini route is incompatible.

## Goal

Make schema qualification capability-first by reading the canonical aggregate
schema generated by the configured Desktop App Server. Preserve fail-closed
behavior for missing, oversized, malformed, or incomplete protocol data.

The change must remain local to the thin App Server compatibility adapter.

## Non-goals

This change will not:

- remove or bypass App Server compatibility qualification;
- accept a version merely because its number is known;
- increase the directory-wide file-count limit or parse every generated schema;
- change the executor, MCP contract, approval policy, workspace policy, routing,
  runtime layout, or 9Router Responses adapter;
- add a new dependency or change provider credentials;
- delete the currently installed `c97e934d` companion release or its rollback
  checkpoint.

## Design

### Canonical schema source

The adapter defines one canonical generated-schema filename:

```text
codex_app_server_protocol.schemas.json
```

`readGeneratedSchemas` reads exactly this file from the disposable schema
output directory. It does not enumerate, count, or parse sibling JSON files.
This makes qualification independent of how many split schemas a future Codex
Desktop version emits.

### Validation

The existing 4 MiB maximum applies to the canonical file. The adapter parses
the file as JSON and requires both:

- `definitions.ClientRequest`;
- `definitions.ServerRequest`.

The stable qualification and approval qualification consume these definitions
from the same parsed bundle. Existing request/event subset checks remain in
force.

The adapter continues to fail closed with the existing compatibility error
boundary when the canonical file is:

- missing or unreadable;
- larger than 4 MiB;
- invalid JSON;
- missing either required definition;
- structurally incompatible with a required stable or approval capability.

The user-facing failure remains `Codex version chưa được hỗ trợ`, with sanitized
version/hash diagnostics. A version or hash change alone remains a warning and
does not override capability evidence.

### Scope boundary

Only the schema-loading seam and its focused tests may change. No raw App Server
protocol handling may escape the compatibility adapter, and no fallback to a
different executable on `PATH` is introduced.

## Test Strategy

Implementation follows a red-green-refactor sequence:

1. add a regression test whose generated-schema directory contains more than
   64 sibling JSON files plus a valid canonical bundle;
2. prove the current implementation rejects that compatible fixture;
3. change the loader to read only the canonical bundle;
4. prove the regression test passes;
5. retain or add focused failures for missing, oversized, invalid, and
   incomplete canonical bundles where current coverage is insufficient;
6. run the complete companion test suite with bounded concurrency.

The regression test must use synthetic local fixtures. It must not depend on
the disposable schema directory under `C:\tmp\CodexScratch`.

## Installation and Acceptance

After tests pass and the code is committed as a separate rollback point:

1. create a new immutable companion installation named by the new commit;
2. preserve the existing `c97e934d` installation for rollback;
3. create a configuration checkpoint before changing the MCP registration;
4. update the registration through the exact Desktop App Server executable and
   the prescribed safe scripts or CLI path, never by manually editing
   `config.toml`;
5. confirm the registered server exposes `run_gemini_task`,
   `get_gemini_status`, and `cancel_gemini_task`;
6. run one elevated, bounded live request with the exact expected result marker
   `COMPANION_INSTALL_OK`;
7. confirm evidence for `Codex -> 9Router -> Gemini route -> upstream success ->
   response to Codex` and confirm the task made no workspace file changes.

No repeated live loop is authorized. If this one request fails, classify the
failure at the first observed boundary and stop rather than retrying broadly.

## Security

- The Gemini/9Router API key remains outside committed files and is never
  printed in logs or reports.
- Qualification continues to pin and record the exact Desktop App Server path,
  version, and SHA-256.
- Generated schema data is size-bounded and parsed only from the expected
  canonical filename.
- Staged changes must pass Gitleaks before the implementation commit.
- Dependency manifests are not expected to change; if they do, OSV coverage is
  required before commit.

## Rollback

Rollback restores the pre-change MCP registration from the configuration
checkpoint, or points it back to the retained immutable `c97e934d` release.
Neither rollback path changes 9Router data, Desktop installation files, the
normal ChatGPT Plus route, or user workspaces.

No old release, runtime record, checkpoint, or disposable test directory is
deleted automatically.

## Acceptance Criteria

The change is accepted only when:

- a compatible canonical bundle passes even with more than 64 sibling schemas;
- all missing, oversized, malformed, incomplete, or incompatible canonical
  bundles fail closed;
- the complete companion test suite passes;
- the scoped code diff and security checks pass;
- the new immutable installation passes tool discovery;
- the single live acceptance request returns `COMPANION_INSTALL_OK` through the
  expected Codex-to-Gemini path without changing workspace files;
- the previous immutable installation and checkpoint remain usable for
  rollback;
- unrelated working-tree changes remain untouched.
